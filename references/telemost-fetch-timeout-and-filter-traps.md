## Что ломалось в реальных запусках

- Неправильный фильтр:
  - `--filter telemorest` (`--filter telemost` написан верно)
  - Итог: немедленная ошибка `exit_code: 2` (невалидный filter).
- Долгий/виснущий ответ при `--uid`:
  - Повторялись прерывания и провалы по времени ответа.
  - Причина обычно не в логике фильтра, а в лимитах времени/типа потока ответа.

## Надёжный recovery-паттерн

1. Начинать с корректной минимальной проверки:
   - `--filter telemost --dry-run`
2. Для конкретного документа из списка — использовать точечный `--uid`.
3. Если снова нет ответа: повторить с той же командой и более узким scope
   (`--uid` вместо широкого лимита).
4. Для потенциально долгих выгрузок — запускать в фоне и опрашивать процесс
   (контроль в окружении исполнителя задачи), затем уже разбирать файл в `incoming/...`.

## Справочные соображения

- Для check-only используем minimal form (без лишних флагов), чтобы не раздувать
  время и не менять состояние.
- `--preview-body` включаем только когда нужен текст стенограммы/тела письма
  и пользователь это запросил.
- Ссылаться на локальный файл стенограммы в `yandex-data/incoming/...` после
  успешной выгрузки и только потом строить entity binding.
